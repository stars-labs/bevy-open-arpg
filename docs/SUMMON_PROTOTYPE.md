# 单灵体协同原型

目标：验证“普攻指挥 → 灵体追击 → 技能协同重击”是否有实际玩法区别，再决定第四职业「缚魂使」的完整开发。此原型没有接入职业选择或存档，不代表召唤职业已完成。

## 当前原型范围

- 一个灵体，复用已有原创卫士身体、肢体和剑模型，以半透明青色区分；行走和挥斩使用现有真实肢体动作。
- 只有玩家真实普攻首个有效命中存活敌人，才标记目标四秒。灵体不自行挑选附近怪物。
- 灵体以5.8米/秒接近目标，1.55米内起手；0.32秒普通挥斩的44%接触帧结算一次攻击，基础伤害9，随后0.65秒恢复间隔。
- 玩家技能命中已标记目标，使灵体下一次成功接触强化为25基础伤害，动作切换为0.5秒重劈，在58%接触帧命中；青色标记转金色，成功接触后恢复。一次施法的多个目标/投射物不能重复强化。
- 使用既有敌人伤害结算管线，包括词缀、护卫保护和击杀；灵体命中不再次下达指令、不返还玩家资源、不触发自身循环，也不发起普通命中全局停顿。
- 换目标取消旧攻击；目标死亡、标记过期、主人死亡或目标距主人超过10米，清除标记及强化，回到主人附近。暂停冻结行动、强化窗口和攻击时序。

## 复现

```bash
BEVY_OPEN_ARPG_SUMMON_REVIEW=1 cargo run --locked --features dev_tools
```

新局选卫士，用左键普攻标记，再用E/R命中同一目标。右键移动。该开关仅原生开发构建可用，替代该进程内的原伙伴，以隔离伤害来源；关闭开关恢复原伙伴。

自动录像（需要Xvfb、xdotool、ImageMagick和ffmpeg）：

```bash
python3 tools/ui/capture_combat_growth.py --output target/validation/summon \
  --cases summon-idle summon-empty summon-skill-only summon-mark summon-coop \
  summon-kill summon-leash summon-pause
```

## 本轮不能证明的内容

复用模型是动作实验素材，完整职业需要专属召唤外观。当前灵体不承受伤害，没有召唤物死亡/复活、召回技能、复杂绕障或卡位逻辑；不用于验证这些体验。固定靶用于隔离命令与伤害，不能证明主动敌群或首领战的平衡。第四职业完整技能、天赋与存档也尚未实施。

验收结果将以实际命令输出、动作录像及逐帧数据记录在 `target/validation/summon/`，有失败不得以规则测试替代实机验收。

## 验收结果（2026-10-05）

- 原生真实输入录像八例通过：未标记、空挥、只放技能、普攻标记、协同重击、目标死亡、超距、暂停。
- 固定靶普通灵体命中9伤害，协同命中一次25伤害后恢复9；各帧与玩家伤害分开记账。普通44%、重劈58%接触姿势均与伤害当帧一致。可单独辨识的灵体伤害帧世界速度为1。
- 暂停保持位置、动作与标记窗口约1.47秒；目标死亡及超距清除后没有后续攻击。
- 7项共享命令规则测试、17项资产清单测试、3项特效几何回归通过；开发构建、全功能生产代码检查、默认与开发代码Clippy、格式及正常/灵体模式各120帧第二章启动通过。
- 完整测试与全目标Clippy仍被职业改造遗留的313处旧接口引用阻塞，不能声称全套验证通过。
- 第一轮发现初始化顺序错误：在角色生成前尝试创建灵体，导致特效资源缺失。已改为进入游戏后按依赖顺序创建；最终八段录像及两次无窗口启动均采用修正版本。

录像和数据：`target/validation/summon/<case>/contact.mp4`、`summon-frames.json`、`telemetry.json`、`result.json`。自动核对产物：`results.json`、`measured-summon.md`、`verify.log`；构建与测试日志在同目录。

策划结论：协同指挥链路成立，支持继续验证单灵体共战路线。普攻和技能的先后顺序确实决定是否出现重劈；尚不能据此断言长期好玩、群体召唤可行或首领战平衡。换目标及同次多目标去重目前有规则测试，没有多敌人实机录像。后续先补目标优先级的多敌人验收、召唤物受伤/死亡与召回，再做主动敌群及首领试炼，之后才能进入完整第四职业设计。
